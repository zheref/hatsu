# Build — from an issue to a PR standing at the gate

**Nature: Transmuter** for machinery, **Conjurer** for canon/governance, **Enhancer** for product
code; the mode is named at § 2, and said aloud when it switches mid-run.

> **Give me an issue; I execute the canonical Hatsu protocol (§ 4) and deliver a PR that is
> `CON-32`-Ready at its human gate — or a G5 stop saying exactly why it could not get there.**

**Hatsu holds no CI plane to route work to** (no CI routing, stage labels, waves or wake
ladders): building an issue runs the local-plane pipeline — [`ten`](../ten/SKILL.md) warms up,
[`classify`](../classify/SKILL.md) labels the two axes where unlabelled, [`direct`](../direct/SKILL.md) picks
model, surface and effort against this session's, [`ren`](../ren/SKILL.md) authors and verifies,
[`aka`](../aka/SKILL.md) publishes, [`mukai`](../mukai/SKILL.md) reviews, tests, measures coverage and opens the PR (pickers: jutaisho § 4),
[`en`](../en/SKILL.md) drives it to readiness, [`rikugan`](../rikugan/SKILL.md) renders the delivered state,
and [`cleanup`](../cleanup/SKILL.md) § 2 is offered once its prerequisites hold.

**The phases this composite calls skip their own `## 0.`**
([`docs/STANDALONE-ENTRY.md`](../../../docs/STANDALONE-ENTRY.md) § 4); the plugin root is
[`docs/PROCESS.md`](../../../docs/PROCESS.md) § *Authority every phase shares*.

## 2. Inspect the issue and confirm the mode

Read the issue first:

```bash
gh issue view <N> --repo <owner/name> --json title,body,state,labels,closedByPullRequestsReferences
```

- **If closed**: the run ends immediately, reporting what closed it and which PR delivered it (from
  `closedByPullRequestsReferences`).
- **If an epic awaiting approval**: stop at **G1** (row `mode-label`) — the mode label is the
  maintainer's decision (`CON-4`), never an agent's.
- **Read requirements**: title, body, acceptance criteria, constraints, then its shape
  ([`plugin-registries`](../../../docs/config/plugin-registries.md#contractsissue-sectionsjson), *The check*; HR-4): an open `OQ-{n}`
  row is a **G1** `DECIDE`, `next: clarify`, never answered here (futon § 2 skips it); a miss never stops; exit `2` or an unread issue a G5.

**Confirm Kurapika's work-mode** from the domain and nature of the issue:

| Issue domain / content | Mode |
|---|---|
| Product code, UX, customer-facing behaviour | **Enhancer** |
| Canon prose, governance, specifications, schemas | **Conjurer** |
| Machinery, tooling, workflows, scripts | **Transmuter** |

**With ambiguity, propose one and ask** (a `DECIDE`, [`jutaisho`](../jutaisho/SKILL.md) § 4, row
`mode-unknown`, once per run).

## 3. Worktree isolation by default

All authoring, feature work, and verification for the issue **must run in an isolated git worktree**
([`docs/WORKFLOW.md`](../../../docs/WORKFLOW.md) § *Where worktrees live*):

```
<core>/.nen/worktrees/<surface>/<name>
```

Git-ignored inside core, never a sibling; branch `{model}/{persona}/{descriptor}` (`nen/workflow.json`); core
stays clean and parked on the trunk unless the maintainer's own prose says to work on core. **One checkout per
concurrent effort** (step 2 there; hatsu#229): a second issue is never started
in an occupied worktree — it gets its own `<name>` — and a tree a reviewer is reading is never switched
under them: hanten § 4's detached checkout exists for that, and where the isolation hook refused it, the
run waits for the review to return (a moved ref is hanten § 4's G5).

## 4. Building protocol
