# Senkei — inventory a product repo's own backlog and state each PR's readiness

**Nature: Manipulator.** GitHub-side reading and reporting over **one consuming product repo's** own
backlog. Kurapika says so when he runs it.

This is the product-repo counterpart of [`backlog-loop`](../backlog-loop/SKILL.md), which drives Hatsu's
own backlog. Senkei never touches Hatsu's backlog. It enumerates (§ 2), classifies (§ 3), states a
`CON-32` determination for every open PR (§ 4) and reports (§ 5). **It calls none of the five
human-called phases** — `aka`, `mukai`, the merge, `kagutsuchi` and `mugetsu` are the maintainer's
([`WORKFLOW.md`](../../../docs/WORKFLOW.md) § 4) — and prompts for none. **Senkei itself** opens, pushes,
merges, uploads, publishes and edits nothing; a PR it hands to `sharingan` (§ 4) runs under sharingan's
own authority. It is reached only by its typed call; no composite runs it and Illumi's loop does not
(ROSTER OPEN-1). The evidence for each verb below is [`docs/ab/senkei.md`](../../../docs/ab/senkei.md)
§ *Re-run of 2026-11-03*, which also lists what it did not exercise.

## 1. Invocation

```

```

**P1 — the run opens with `/ten senkei`, never skipped.** Ten's target is the checkout senkei runs
from, never the product repo; ten § 6 reads senkei as a phase owning its catch-up, steps 4 · 5. **The
phases this composite calls skip their own `## 0.`** and inherit P1–P4 from this run
([`STANDALONE-ENTRY.md`](../../../docs/STANDALONE-ENTRY.md) § 4); each says which composite holds it.

`<repo>` is a product code, a short name or an `owner/repo`, taken from the invocation, **never
guessed**:

```bash

nen repo resolve <token> --repo <a checkout carrying the registry that records the target>
nen repo resolve all --repo <that checkout>
nen repo scenario --repo <that checkout> --target <owner/name>
```

An empty slot (`nen parse` exit `2`) lists the codes with `resolve all` and asks; an unknown token

order** — the canon registry, then the product repo's own `nen/repos.json` where it records itself with a
`scenario` — never the product repo's checkout as a stand-in for a registry it does not carry. **An
unregistered product repo is reported, never written**: senkei names the missing `consumers` entry and
the repository that owns the registry, and stops that repo's run. Resolve once; carry the slug forward.

reported **unread** (never "declares no stages") and § 4 passes identities by flag. Its declarations are

`nen/gates.json` is a finding for **that repo's maintainer**, landed as a PR at that repo's own gate.
Readiness (§ 4) does not depend on it.

## 2. Enumerate — `nen repo inventory`

```bash
"$hatsu_root/scripts/gh_token_env.sh" nen repo inventory --target <owner/name> --epic-label <label> --integration-prefix <prefix> --trunk <branch.base>
```

Every open issue carrying `--epic-label` with its children, every branch under `--integration-prefix`
with its ahead/behind against `--trunk`, and every open PR. **Always fetched live**; never a cached list.

- **`--epic-label`** and **`--integration-prefix`** are the target's own conventions, read from its
  label declaration and branch names, never hard-coded or copied from another repository. A target that
  declares no epic label reads `epics: 0`, which is the label's absence, not an empty backlog: say so.
- **`--trunk`** is the target's `branch.base`, `main` where none is declared.

An integration branch alive with no open epic to own it is the `idle` shape (§ 3), reported for cleanup.

## 3. Classify — `nen effort classify`

| Class | Meaning |
| --- | --- |
| **delivering** | A delivery PR is open at **G2** — the final integration-to-trunk PR, or a child PR delivered alone. |
| **building** | A child released into building (a released stage label); no PR yet, or a PR in review. |
| **stalled** | Released with no branch or PR ever opened, or a reviewer job that never posted its verdict. |
| **queued** | G1-approved (a mode label picked) but not yet released with a stage label. |
| **idle** | An integration branch still alive whose epic is closed: flag it for cleanup. |

**The verb prints seven values; two are answers *about* the taxonomy, not classes, and the report
handles both by name**: `state-machine-violation` (two released stage labels on one object — flagged,
never resolved by guessing which is authoritative) and `undecidable` (nothing places the object
anywhere — reported as such, never folded into `queued`).

```bash
nen effort classify --input <absolute path.json> --repo <the product repo's checkout>
```

**The stage family is the target's own declaration**: every `<namespace>:stage/<leaf>` label its
`nen/labels.json` declares, nen's definition (`nen stage --help`). **A target that declares none** has
no stage-based class to claim: every `stageLabels` is empty, `modeLabelPresent` false, and the report
says the repository declares no delivery stages ([`WORKFLOW.md`](../../../docs/WORKFLOW.md) § *A target
repository with no delivery-stage taxonomy*).

**Sort the family's leaves before the classifier, or it misclassifies silently.** The input is one
`{kind, issueState, stageLabels[], modeLabelPresent, hasPr, prOpen, prIsDelivery,
integrationBranchAlive, reviewerVerdictMissing}` per effort, and the verb reads only the label text it is
given:

- **G1 mode leaves** (the ones the maintainer picks at G1, `CON-4`) become `modeLabelPresent: true`,
  **never** `stageLabels` — passed there, a G1-approved epic reads `building` instead of `queued`.
- **Pre-G1 leaves** (an idea, a triage or a research stage) are left out of the pass and reported as "not
  yet G1-approved" — passed in, they read `stalled`.
- **Released leaves** go in `stageLabels`. Two on one object is the `state-machine-violation`, judged on
  this sorted set only: a mode leaf beside a released one is not a violation.
- **Which leaf is which is the target's declaration.** Where it does not say, ask once per run
  (`missing-configuration`); the answer is used for this run, and recording it is a PR at that
  repository's own gate. Never infer a leaf's kind from its name.
- **`reviewerVerdictMissing`** is caller-supplied: set it only on a dead reviewer job confirmed in § 4.

Pass an absolute `--input` and a deliberate `--repo`: a relative input resolves against `--repo`'s root,
never the calling directory.

## 4. State every open PR's readiness — `nen pr ready`

For each open PR, a **Ready / not-Ready** determination with its reason — never "checks are green".

```bash
"$hatsu_root/scripts/gh_token_env.sh" nen pr ready <N> --gh-repo <owner/name> --repo <the product repo's checkout> --explain
```

The verdict is quoted **verbatim**; it is never re-derived from the check rollup by eye, and the
adversarial confirmation pass may only veto a `ready`, never promote a `not-ready`
([`pr-state`](../pr-state/SKILL.md)).

**Reviewer identities are the target's own.** Its `nen/gates.json` needs no flag. Without one, `nen pr
ready` refuses at exit `2` and never guesses a reviewer set. Then pass `--reviewers` and `--approvers`
read from **that repo's own** review configuration — `--approvers ""` only for a declared
`review-round-only` policy — and say every time that a flat list cannot express a conditional member,
the `aiReviewers` reading or a kind-bot waiver, which only a `nen/gates.json` models. **Never reuse
Hatsu's `contracts/reference.gates.json` or another repository's identities.** With neither, the
identities are the maintainer's word (row `missing-maintainer-choice`, `senkei <reviewers>`): ask, offer a
`nen/gates.json` as that repo's own declaration PR, and with no answer the refusal **is** the report.

Name these failure modes in the determination when they apply:

- **A reviewer job that died mid-run**, leaving a stale verdict on a required check. The rerun is a
  GitHub mutation with no dry run that re-executes the target's CI with its secrets, so it runs only on
  the maintainer's per-action confirmation naming the target, the run id and the run's head SHA; a run
  whose head is not the PR's current head, or a fork-headed run on a self-hosted runner, is refused:

  ```bash
  "$hatsu_root/scripts/gh_token_env.sh" nen run rerun-failed --target <owner/name> --run-id <n>
  ```

  **Never re-label to force a re-vote.**
- **An author that stopped mid-run** and pushed nothing: `stalled` in § 3, not `building`.
- **Two released stage labels on one child**: `state-machine-violation` (§ 3).

**A PR stuck for any other reason goes to [`/sharingan`](../sharingan/SKILL.md)**, once per stuck PR,
under sharingan's own authority. Senkei fires no label and no wake: Hatsu holds no CI plane
([`WORKFLOW.md`](../../../docs/WORKFLOW.md) § *Building an issue with no CI plane*). **Senkei requests no
reviewer round; sharingan does, under its § 6 and the decision row it cites there.**

## 5. Report — the bell, then rikugan's `register`

**The bell is [`jutaisho`](../jutaisho/SKILL.md)'s, rung before the register.** A pass rings rung 1. An
ask from an `ask-once-per-run` row (`missing-argument`, `missing-configuration`,
`missing-maintainer-choice`) takes the picker and rung 1, no banner. Senkei raises no gate stop of its
own: a PR Ready at G2 is the maintainer's merge, shown in the register, never prompted.

Then hand the scope to [`/rikugan`](../rikugan/SKILL.md) as `register` (its § 2 row 1, `from:
senkei`): every epic, child, integration branch and PR § 2 listed. The desk carries § 3's class for each
object, the objects left out as not yet G1-approved, and § 4's verdict quoted for each PR. Cite objects
in the target's own notation, from the registry § 1 resolved:

```bash
nen ref format --repo <the registry checkout § 1 resolved> --code <CODE> --kind <IS|PR> --number <N>
```

## Authority

- **No new authority.** The run-scoped label delegation belongs to
  [`backlog-loop`](../backlog-loop/SKILL.md) by name; senkei applies no stage label without the
  maintainer's per-action confirmation, and no routing label at all.
- **No merging, anywhere.** G2 is the target repo's maintainer's.
- **No writes by senkei itself** to the target's code, declarations or PRs. A PR handed to `sharingan`
  is that skill's to drive, pushes and round requests included.

## Hard limits

- Never merge, on any repository, for any reason.
- Never apply a label without the maintainer's per-action confirmation.
- Never rerun a reviewer job without the maintainer's per-action confirmation naming target, run id and
  head SHA, and never one whose head is not the PR's current head (§ 4).
- Never cast a `request_changes` review or fire a label to move a stuck PR — hand it to `sharingan` (§ 4).
- Never guess the target repository (§ 1), a reviewer set (§ 4) or a stage leaf's kind (§ 3).
- Never feed a mode or pre-G1 leaf into `stageLabels` (§ 3).
- Never restate the reviewer-round bounds; `sharingan` § 6 holds them. `nen/workflow.json` →
  `monitor.maxCycles` is en's acting-cycle cap, a different number.
