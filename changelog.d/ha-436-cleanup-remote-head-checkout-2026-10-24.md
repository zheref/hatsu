### Fixed

- **`cleanup` names the checkout a remote-head delete runs from when no worktree is left (zheref/hatsu#436).** § 5 had a push shape only for an effort worktree, so on the HA-IS-#426 sweep a merged remote head whose worktree was gone got a row pushing from core, which sits on the trunk and is refused by `hooks/guard-base-branch.sh`. Now every remote-head row, deterministic or proposed, names its host, and `<branch.base>` is never a remote-head row. That includes a merged head whose worktree is kept (dirty, locked or not admitted), and the clean effort-worktree sequence, whose push is now that same row with its own worktree as host, so a moved SHA there has an outcome too. The row first runs `git -C '<host>' ls-remote --heads origin -- 'refs/heads/<branch>'`, which must print only `<sha>\trefs/heads/<branch>` with the SHA pass 1 recorded, else the row runs nothing and is reported. Then it runs `git -C '<host>' push origin --delete -- '<branch>'`, where `<host>` is a literal path: the head's own worktree when § 4's admission admitted it, else another admitted path. An admitted path is never on `<branch.base>` (condition 6 of `cleanup_path_admit.ts`'s header), so the trunk guard lets the push through, and core is never the host. The host goes in the row's evidence. Every push runs before any `worktree remove`, and § 6's pass 2 says so ("every push first"), so the host is still there when its row runs. With no admitted path, the row is **named** (`no admitted checkout`, now in the "Named facts win" list) and never given a command that cannot run as written.
