### Added

- **Hatsu's shell guards are measured on their focused lanes (zheref/hatsu#148, UZF-19).** Twenty-five of the 38 shell lanes now run their script through `scripts/shell_coverage.mts`: with the pinned Bashcov 4.0.0 (activated at that exact version through RubyGems, so a user gem home off `PATH` still resolves), SimpleCov 1.3.2, simplecov-lcov 0.9.0 and a Bash 5+, the `test` row writes `coverage/<lane>/lcov.info` and nen records its capture, and each lane's new extraction-only `coverage` row (which refuses a report whose recorded file digests no longer match the tree) is read, as byakugan now does, with `nen shu coverage --lane <lane> --touched --base origin/<base> --from-capture`, which runs no fixture. `project.toolchain` declares the five host rows (`ruby` and `bash` verify-only, the three gems `gem-user`), so `nen shu tools --repo . --install` provisions them. Without Bashcov a fixture still runs, once and uninstrumented, says so on stderr and leaves no report, so `--from-capture` refuses for want of a capture rather than reading an old number; `HATSU_SHELL_COVERAGE=0` skips the instrumentation and `require` refuses without it. A POSIX `sh` fixture runs under `sh` first, then instrumented. A trace Bashcov cannot parse captures nothing; a passing run stays green, and a failing one is re-run plain, whose exit decides. SimpleCov is activated at its pin before Bashcov, and each installed `.gem` is checked against the contract's `gemSha256` (nen's `gem-user` installer pins by version only); a mismatch refuses. The gems are on no dependency-audit row: not scanned. A `nen shu tools` exit `5` on these coverage-only rows alone reads *unmeasured, still testable* (`docs/PROCESS.md`, breath § 2c, ten § 1, bankai-quality). The helper refuses any invocation its lane does not declare, a symlinked fixture, and an LCOV source outside the repository; its own fixtures (`scripts/shell_coverage_fixture.test.mts`) run in the `unit-tests-ci-guard` lane. `scripts/shell_coverage.mts` joins `PLUGIN_SURFACE_GLOBS` in `scripts/plugin_bump_check.sh`, because ten's `nen shu tools --repo <hatsu_root>` runs the `bash` row's probe out of an installed copy. The other thirteen seat their `coverage` row with the measured reason instead of a number: in eight the trace of a child shell reaches the output the fixture asserts on (macOS `/bin/sh`, bash 3.2, ignores `BASH_XTRACEFD`; `publish-integrity-guard` among them, which is also red uninstrumented under an empty or C locale and green under UTF-8), three produce a trace Bashcov 4.0.0 cannot parse, and two (`trusted-guard-preflight`, `redaction-tree`) are red uninstrumented on the measuring host and on the untouched base, under UTF-8 too. The `plugin` lane's `coverage` seat now says where shell coverage lives and keeps the TypeScript guards as an unmeasured gap. The 80/85/90 ladder is unchanged.
- **`config-values-guard` runs in CI, step one (zheref/hatsu#397, BC-9).** `scripts/unit_tests_ci.mts` selects the lane whenever `scripts/config_values.ts` exists beside `scripts/config_values_examiner_fixture.ts`, and its fixture proves the selection, the missing-fixture refusal and a red lane failing the run. The runner is the base revision's trusted copy, so the lane runs from the first pull request whose base carries this change; step two is that pull request's `unit-tests` log naming the lane, plus a non-draft probe pull request breaking the examiner fixture that turns the check red; HA#397 closes on that evidence. The lane also declares its `coverage` row: Bashcov measures `scripts/config_values.sh` and its fixture, while `scripts/config_values.ts` stays in the TypeScript gap.
