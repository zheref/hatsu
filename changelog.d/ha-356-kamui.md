### Added

- **`hatsu:kamui` — one feature written once as the product's spec, then ported to the siblings you pick** (plugin `0.125.0`; zheref/hatsu#356, child 2 of the cross-platform porting epic zheref/hatsu#354). `hatsu:kamui <CODE>-IS-#<N> | <CODE>-PR-#<N> [--dry-run]` writes the source issue (or a merged PR and its closing issues) as a `github/spec-kit` set in the product family's **spec repository**. The set is pinned at `v1.2.2`, read live on 2026-10-20: `specs/<nnn>-<slug>/` with `spec.md`, `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, `contracts/`, `tasks.md` and `checklists/requirements.md`, plus `.specify/memory/constitution.md` once, which cites `CON-{n}` and never overrides it. The spec repository is searched first for the source and its linked objects, each matched as a fixed string on word boundaries, so a later port of the same feature amends its folder. The spec PR runs `ren → aka → mukai → en` to the **G2** merge prompt, and nothing is built before it merges: the wait is `nen watch until` on the PR's state; `CLOSED` ends the run *spec declined*, and an observation-error streak is a G5. Then the sibling picker asks which configured siblings get a port issue (new `nen/decisions.json` row `port-siblings`). It is never starred, pages in fours, and asks even for a lone sibling. Its answer is the G1 for one port issue per pick through `file` §§ 3–5, written by `nen issue file --assignee` and read back explicitly. Next, a start picker runs the picks as `hatsu:build` one after another. Kamui holds build's register and wrap-up, and a build's G5 stops the chain. Missing setup is asked per item, in order; creating the spec repository is a G5 hand-over line, given only when gh says the repository does not resolve. A member whose visibility reads public never receives the family.
- **`docs/config/ports.md`**: the checkouts file (tab-separated, each path's `origin` verified before use) and the run record `${XDG_STATE_HOME:-$HOME/.local/state}/hatsu/ports/<run-id>.json` (`schema` `hatsu.port.run/v0.1`). `hatsu:kamui resume <run-id>` validates the id's shape before building any path, and recomputes the step from live state, so a record can never skip the merge wait. `hiraishin` (#357) and `bankai-rule` (#355) cite this page.
- **`families[]` and the `spec` role, documented on the Hatsu side**: `docs/config/repos.json.md` § `families[]`, with three redacted fixtures under `scripts/fixtures/port-family/` (the spec repository's registry, a member's, a registry with no family). All three exit `0` through `nen schema check` at nen `0.22.0`, with `families[]` tolerated but not validated until zheref/nen#453, and an absent `gates.json` warning. The spec repository lists itself under its own `consumers[]`, so it reads **G2**. A family is declared only in its members' and spec repository's own registries, never in Hatsu's. Owed to nen: zheref/nen#453 (the key and the role), zheref/nen#454 (`watch until --until merged`), and zheref/nen#444, amended with `issue file --title-file`. Cited: the prose pack, zheref/nen#450. The slug-shaped `fixture-*` placeholders join `docs/PUBLIC-REDACTION.md`'s legend.
- **A ninth catalogue domain, `port`**, with `workflow.port.specKit.pin` (`v1.2.2`) and `workflow.port.specKit.layout` (`specs/{nnn}-{slug}`), both gated `when: nen/workflow.json#port` so `fill` never writes them into an unrelated repository; documented in WORKFLOW § 2 → `port` and `docs/config/workflow.json.md`.
