### Fixed

- **The Node dependency audit reads the repository's own lockfile and asks OSV, executing nothing ([#247](https://github.com/zheref/hatsu/issues/247), item 1).** `contracts/scans.json` (now `hatsu.scans/v0.2`) → `dependencyAudit.node` was a single `npm audit --audit-level=high` row. That command exits `ENOLOCK` on a pnpm tree, so every adopted Node consumer (each pins pnpm through `packageManager`) was reported *not scanned*. Running the matching package manager instead would execute the reviewed tree's `.pnpmfile.cjs`, `yarnPath` and `.corepack.env`, follow its `.npmrc` registry and send its tokens there. So the row works the way the swift row does:
  - `packageManager` selects the manager. The one lockfile present selects it only where the field is absent.
  - The lockfile is parsed strictly: pnpm at lockfileVersion 5, 6 and 9; yarn Berry and classic, by declared markers, split on column-0 headers, with npm aliases read as the real package; npm 1 to 3. A line the parser does not read, a truncated file or entry, or a registry-shaped entry that does not parse is *not scanned*, never skipped.
  - An entry is queried only when it has no resolved URL, or one on a declared `registryHosts` host. Git, `file:` and foreign tarballs are *unqueried*, and an unqueried entry is never clean.
  - Every registry `package@version` is posted to OSV `querybatch` at ecosystem `npm`. Each returned id's GHSA severity is read against `severityFloor`; a missing or unknown severity is `UNRATED` and counts.
  - The answers are bounded by `timeoutSeconds` and `maxResponseBytes`, and the lockfile by `maxEntries` and `maxDepth`. A malformed answer is *not scanned*. The two OSV endpoints are the only hosts contacted, and no environment is sent.
  - Redirect and suppression keys, and another lockfile beside the selected one, are printed as `audit-config:` evidence and never honoured.
- **Rows are selected by stack.** Each `dependencyAudit` row declares the `nen repo classify` stacks it answers: `node` takes `nextjs`, `gatsby`, `expo`, `react` and `electron`; `swift` takes `xcode-ios` and `xcode-macos`; `jvm` takes `gradle-android` and `compose-desktop`. `dotnet-winui`, a null stack and Hatsu's own `claude-code-plugin` are *not scanned*, by name. `stackCatalogue` snapshots nen's stack vocabulary, and the fixture fails when a stack is neither routed nor named.
- **`scripts/dependency_audit_resolve.mts`** answers exit `0` (clean), `1` (a finding or an unqueried entry, never clean), `3` (not scanned, named) or `2` (wiring, including any internal error). Its command is the node row's `run`. Hanten § 2a and Feitan's table name the selection, and `docs/config/plugin-registries.md` lists the new keys with their types. `docs/PROCESS.md` § *Residue* records the resolver and the swift row's OSV route as owed to nen. The script joins `PLUGIN_SURFACE_GLOBS`. Its hermetic fixture runs as lane `dependency-audit-guard`, in `unit-tests.yml` through `scripts/unit_tests_ci.mts` once this lands. It uses a loopback stub OSV, and proves a pnpm tree is scanned and its finding reported. Its hostile tree runs no hook, sends no canary or token, and cannot read clean.
