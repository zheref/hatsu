### Fixed

- **`scripts/pr_body_delivery_check.sh` renders the Delivery expectation from Hatsu's own `templates/pr-delivery.md`**, resolved beside the script, instead of `<--repo>/templates/pr-delivery.md`. A consumer carries no such file, so on any non-Hatsu target (zheref/nen's NN-PR-#507 the first seen) the guard exited 2 with `could not read '<target>/templates/pr-delivery.md' (ENOENT)` and could never pass; a target that did carry one would have had its own text checked as the expectation. `shibari` § 3's manual Delivery render now names `"$hatsu_root/scripts/pr_delivery.ts"` and `"$hatsu_root/templates/pr-delivery.md"` for the same reason. The guard resolves its own directory physically (`cd -P`, `CDPATH` cleared), and `scripts/pr_delivery.ts` compares real paths before running, so a call through a symlinked plugin root (`~/.claude/skills/hatsu` is one) no longer exits 0 having written nothing.
- **The guard and its engine are plugin-shipped paths.** `scripts/pr_body_delivery_check.sh` and `scripts/pr_delivery.ts` join `PLUGIN_SURFACE_GLOBS` beside the evidence and Development guards, so a change to either needs a version bump and reaches cached installs; this release is `0.138.1`. `CONTRIBUTING.md`'s copy of the list is re-synced, picking up `scripts/issue_body_check.mts` and `scripts/pr_criteria_check.mts` it had missed. Installed copies get the fix by updating to `0.138.1`.
- The delivery fixture runs the guard against a target with no `templates/`, with a planted template it must ignore, from a plugin root with no template (refused, naming the plugin's path), and through a symlinked plugin root; each fails against `main`'s guard or engine.
