### Added

- **Every outstanding `hatsu:tenkai` item now names its fix, and the report offers a guided fill (zheref/hatsu#535).** After a scaffold, Tenkai counted the items still carrying placeholder commands — the scaffold's `PROPOSED SEAT` rows, actions ending in `--repo <path>`, `<id> --value <JSON>` — and gave no next step. `scripts/tenkai_adopt.sh` now attaches a `fix` block to every outstanding row, rendered from the new `contracts/tenkai-fixes.json` by `scripts/tenkai_fixes.ts`: the `run` line with the target filled in, the file and key to `edit`, the `detect` command that reads the item again, and `fill` — `default` (apply writes only catalogue defaults and Hatsu seeds), `owner` (the run takes the owner's answer in the `<token>` its `asks` names) or `edit` (a structure `nen schema set` never replaces, such as a seat, edited by hand after the owner decides). The engine's `--repo <path>` placeholders print the real target. The report ends with a `guide` in those three groups, and `tenkai` § 7 relays each fix and offers the guided fill, re-running `diagnose` after each group so the count is seen going down; Tenkai never invents a value. New lane `tenkai-fixes-guard` (`scripts/tenkai_fixes_fixture.test.mts`, selected by `scripts/unit_tests_ci.mts`) proves the catalogue's shape, a named fix for every id the engine emits, and the count dropping after apply, after an owner-answered run line and after an owner's edit.
