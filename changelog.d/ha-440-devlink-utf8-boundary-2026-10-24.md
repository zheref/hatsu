### Fixed

- **The Development-link guard reads valid UTF-8 on macOS (zheref/hatsu#440).** `scripts/pr_development_link_check.sh` checked encoding by sending `iconv -f UTF-8 -t UTF-8` to `/dev/null`, and macOS's `/usr/bin/iconv` fails writing a character device when a valid multibyte character straddles its 1024-byte buffer. So a body was refused as `not valid UTF-8` depending only on where a `·`, `→` or emoji landed, and `shibari` § 4 and `en` § 4 stopped on a body that was fine. The check now writes to a private file in the guard's own work directory and removes it. A body that is not valid UTF-8 is still refused with the same message. The self-test adds a case beside `invalid UTF-8 is refused`: a `·`, a `→` and an emoji start at every offset from 1000 to 1100, and the case reports the first offset refused. On the macOS host, the old check refuses at offset 1014. No other script has the same `iconv … > /dev/null` shape: `scripts/prose_size_check.sh` already checks with Perl's strict decoder for this reason.
