### Fixed

- **The Development-link guard decodes UTF-8 with Perl's `Encode` (zheref/hatsu#440).** `scripts/pr_development_link_check.sh` checked encoding by sending `iconv -f UTF-8 -t UTF-8` to `/dev/null`. macOS's `/usr/bin/iconv` fails writing a character device when a valid multibyte character straddles its 1024-byte buffer, so a body was refused as `not valid UTF-8` depending only on where a `·`, `→` or emoji landed, and `shibari` § 4 and `en` § 4 stopped on a body that was fine. The same iconv also passes a code point above U+10FFFF (`F4 90 80 80`) and the lead bytes `F5`–`F7`, which are not UTF-8. The guard now decodes with `Encode`'s `utf8` decoder under `FB_CROAK`, writing no output, and then refuses a surrogate and any code point above U+10FFFF. It refuses a stray, truncated or overlong sequence, a surrogate, a code point above U+10FFFF and a lead byte `F5`–`FF` with the same message as before. Noncharacters such as U+FFFE and U+10FFFF are valid UTF-8 and are read. A body path that starts with `-` is read as a file, never as a `perl` or `cmp` switch. A decoder that cannot run is exit `2`, quoting the decoder's first error line, and is never reported as `not valid UTF-8`. The guard now needs `perl` instead of `iconv`, and `PR_DEV_LINK_PERL` names the perl to run under the same never-a-verdict rule as `PR_DEV_LINK_AWK`. The self-test adds these cases and a sweep in which a `·`, a `→` and an emoji start at every offset from 1000 to 1100. `scripts/unit_tests_ci.mts` now lists the `development-link-guard` lane. `unit-tests.yml` runs that runner from the base commit, so the lane first runs in CI on a pull request whose base already lists it. It does not run on the pull request that adds it, or on that pull request's integration pull request into `main`, so CI cannot confirm it there. No other script has the same `iconv … > /dev/null` shape.
