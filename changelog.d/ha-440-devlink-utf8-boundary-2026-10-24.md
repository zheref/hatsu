### Fixed

- **The Development-link guard checks UTF-8 with a strict decoder (zheref/hatsu#440).** `scripts/pr_development_link_check.sh` checked encoding by sending `iconv -f UTF-8 -t UTF-8` to `/dev/null`. macOS's `/usr/bin/iconv` fails writing a character device when a valid multibyte character straddles its 1024-byte buffer, so a body was refused as `not valid UTF-8` depending only on where a `·`, `→` or emoji landed, and `shibari` § 4 and `en` § 4 stopped on a body that was fine. The same iconv also passes a code point above U+10FFFF (`F4 90 80 80`) and the lead bytes `F5`–`F7`, which are not UTF-8. The guard now decodes with Perl's `Encode` in strict mode, as `scripts/prose_size_check.sh` already does, and writes no output. It refuses a stray, truncated, overlong or surrogate sequence, a code point above U+10FFFF and a lead byte `F5`–`FF` with the same message as before. A decoder that cannot run is exit `2`, never `not valid UTF-8`. The guard now needs `perl` instead of `iconv`, and `PR_DEV_LINK_PERL` names the perl to run under the same never-a-verdict rule as `PR_DEV_LINK_AWK`. The self-test adds the U+10FFFF and `F5` refusals, a decoder failure, and a sweep in which a `·`, a `→` and an emoji start at every offset from 1000 to 1100. `scripts/unit_tests_ci.mts` now runs the `development-link-guard` lane on every pull request whose base carries the guard. No other script has the same `iconv … > /dev/null` shape.
